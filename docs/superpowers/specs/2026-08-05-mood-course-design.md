# 무드 기반 탐색과 코스 빌더 — 설계

작성일 2026-08-05 · 대상 AROUND (around-culture-map)

## 1. 배경

AROUND는 서울의 문화 행사를 지도와 AI 큐레이터로 탐색하는 프로토타입이다. 지금까지 지도는 위치만 보여줬고, 의미는 전부 사이드바 목록에 있었다. 마커에 붙은 번호(`01`, `02`, `03A`)는 `Map` 순회 순서일 뿐 아무 정보도 담지 않는다.

제품이 향하는 곳은 두 가지다. 첫째, 바이럴된 뻔한 장소가 아니라 알려지지 않은 장소를 찾는 것. 둘째, 그 장소들로 동선을 짜는 것. 이 문서는 그중 **장소 모델 · 지도 재설계 · 코스 빌더**를 다룬다.

## 2. 범위

포함한다.

- 상설 장소를 1급 시민으로 올리는 데이터 모델
- 무드를 축으로 하는 탐색
- 지도 마커 체계 재설계
- 코스 빌더 — 담기, 순서 바꾸기, 도보 시간, 순서 최적화, 링크 공유
- 새 시각 언어를 사이트 전체 여섯 화면에 적용

제외한다. 각각 별도 설계를 거친다.

- AI 코스 추천 (기존 Groq 큐레이터 확장)
- 사용자 발행 · 계정 · 서버 저장

## 3. 데이터 모델

### 3.1 한 타입에 판별자

현재 `CultureEvent`는 `startDate`와 `endDate`가 필수다. 서점이나 빵집처럼 상설로 열려 있는 곳을 담을 수 없다. 별도 `Place` 타입을 만들면 지도 레이어, 필터, 코스가 전부 두 갈래로 갈라진다. 한 타입에 판별자를 두는 쪽을 택한다.

```ts
kind: "place" | "event"   // 상설 / 기간
moods: MoodId[]           // 탐색의 주축
category: EventCategory   // 메타. 목차의 부제와 상세 정보로만 쓴다
```

기존 43개 항목은 `kind: "event"`를 받으면 그대로 동작한다. 필드를 더하기만 하는 변경이라 마이그레이션이 없다.

**날짜는 당분간 필수로 남긴다.** `startDate`와 `endDate`를 선택으로 바꾸면 9개 파일 37곳이 깨진다 — 전부 값이 있다고 가정하고 읽는다. 지금 43개는 `문화공간` 4곳까지 전부 날짜를 갖고 있어 선택으로 만들 실익이 없다. 날짜 없는 항목이 실제로 들어오는 시점, 즉 수집한 장소를 병합할 때 "날짜 없는 장소를 어떻게 정렬하고 무엇으로 표기할지"를 정하면서 함께 고친다. 그 전에 바꾸면 근거 없이 추측하게 된다.

### 3.2 타입 이름

`CultureEvent` → `Spot`으로 바꾼다. 서점과 빵집이 `CultureEvent`에 담기면 이후 코드를 읽는 사람이 매번 걸린다. 기계적 치환 후 빌드로 검증하며, 타입 검사기가 누락을 잡는다.

### 3.3 무드

일곱 개다. 문구는 행위와 장면을 함께 담되 감정을 싣는 결로 쓴다.

| 무드 | 부제 | 현재 데이터 |
| --- | --- | --- |
| 소리에 잠기는 밤 | 공연 · 리스닝바 | 13 |
| 낯선 것과 마주 서는 낮 | 전시 | 17 |
| 사람 많은 게 좋은 날 | 축제 · 마켓 | 9 |
| 아무 말 없이 오래 | 카페 · 바 | 13 (수집분) |
| 빵 하나에 두 정거장 | 빵집 | 6 (수집분) |
| 먼지 앉은 것들 사이 | 음반 · 헌책 | 0 |
| 해가 낮게 드는 길 | 산책 | 0 |

한 번에 하나만 선택된다. 이 제약이 지도 마커 설계 전체를 단순하게 만든다.

빈 무드는 숨기지 않는다. 목차에 남기되 회색으로 두고 개수 자리에 `—`를 적는다. 앞으로 무엇이 올지 보여주면서 지금 비었다는 사실도 감추지 않는다.

## 4. 화면

세 단으로 나눈다. 왼쪽이 목차, 가운데가 지도, 오른쪽이 코스 트랙이다.

### 4.1 목차

무드 선택을 필터 칩이 아니라 **책의 목차**로 둔다. 각 줄은 무드 문구, 리더 점선, 부제, 장소 수로 이뤄진다. 편집물에는 목차가 있고, 이 제품은 도시를 편집물로 다룬다.

숫자를 목차의 쪽수 자리에 쓰면 지도 마커의 번호는 코스 순서 전용으로 남는다. 두 개의 번호 체계가 충돌하지 않는다.

강등한 `category`는 여기서 부제로 다시 쓴다. 문구만으로는 무엇을 고르는 건지 즉시 읽히지 않는 무드가 있고, 「밤 · 낮 · 날」이 시간 필터로 오해될 여지도 있다. 부제가 둘 다 해결한다.

### 4.2 지도 마커

네 가지 상태뿐이고 흑백만 쓴다. 무드가 한 번에 하나만 켜지므로 마커가 무드를 구분할 이유가 없다.

| 상태 | 모양 | 뜻 |
| --- | --- | --- |
| 무드 밖 | 5px 흐린 점 | 고른 무드에 없는 곳. 도시의 밀도만 남긴다 |
| 담을 수 있음 | 11px 흰 원, 검은 테두리 | 고른 무드의 장소 |
| 코스에 담김 | 30px 검은 원 + 흰 숫자 | 숫자는 **방문 순서** |
| 지금 보는 곳 | 위 + 바깥 링 | 기존 `.is-selected` 펄스 재사용 |

무드 밖 장소는 숨기지 않고 흐리게 남긴다. Mapbox 지명 라벨과 겹쳐 다소 지저분해지지만, "이 동네에 다른 것도 있다"는 신호를 잃지 않는 쪽을 택했다.

`#e61919`은 곧 끝나는 행사 표시에만 쓴다. 그 외에 새 색을 더하지 않는다.

### 4.3 코스 트랙

정류를 세로로 쌓고 사이에 구간을 넣는다. 구간은 세로 점선으로 이어 트랙이 실제 길처럼 읽히게 한다.

```
MY COURSE                3곳 · 73분
─────────────────────────────────
01  가에 서울
    신촌 · 카페
 ┆  도보 6분 · 467m
02  앤드커피바
    신촌 · 카페
 ┆  도보 7분 · 583m
03  투도어
    신촌 · 바
─────────────────────────────────
[ 순서 최적화 ]   [ 링크 복사 ]
```

머리말의 총 시간은 도보 시간과 체류 시간의 합이다. 도보만 적으면 세 곳을 도는 코스가 13분이 되어 사실과 어긋난다. 체류 기본값은 `kind: "place"` 20분, `kind: "event"` 60분으로 고정한다. 장소별로 다르게 두는 것은 이번 범위가 아니다.

### 4.4 좁은 화면

세 단은 데스크톱에서만이다. 태블릿 이하에서 목차는 오버레이로 접히고, 트랙은 기존 `.mobile-panel-handle` 하단 시트를 재사용한다. 새 반응형 체계를 만들지 않는다.

## 5. 시각 언어

Gesso "Obsidian Press" 시스템을 참조하되 색 체계는 받지 않는다. 받는 것은 타이포그래피, 여백, 모션, 디테일링이다. 사이트 전체 여섯 화면에 적용한다 — 한 앱에 두 미감이 섞이는 것이 가장 나쁜 결과다.

### 5.1 참조 원본에서 받지 않은 것

원본 토큰에는 서로 충돌하는 값이 있어 그대로 쓸 수 없다. 판단과 근거를 남긴다.

| 원본 | 문제 | 결정 |
| --- | --- | --- |
| `--gesso-surface` = `--gesso-primary` = `#9d7700` | 카드 배경과 강조색이 같은 값. 같은 문서가 "Never paint large areas with primary"라고 명시 | 앰버 전량 폐기 |
| 중립 램프가 두 벌 (CSS `#8f7229` / JSON `#1e262d`), JSON은 `neutral-950`이 `neutral-50`보다 밝아 단조성이 깨짐 | 어느 쪽도 신뢰할 수 없음 | 기존 AROUND 램프 유지 |
| 컴포넌트 명세의 nav 링크 `#b1bfc5` on `#fffffe` | 1.89:1. WCAG 크게 미달 | 폐기 |
| Do는 "high-contrast SERIF for display", Don't는 "Never set headlines in a geometric sans", 실제 디스플레이 서체는 기하학적 산세리프 Sora | 산문 규칙끼리 자기모순 | 토큰(Sora)을 따름 |
| radius 토큰 2px / 레퍼런스 HTML 8px | 불일치 | 레퍼런스 HTML |
| 캔버스 `#fffffe` | 같은 문서의 "always carry warm paper tint"와 어긋남. 지도가 화면 절반을 차지해 눈부심 | 기존 `#f1f0ec` 유지 |

### 5.2 토큰

```
--paper   #f1f0ec   바탕
--white   #faf9f5   융기면
--ink     #11110f   본문 · 강조 면 (16.58:1)
--muted   #5a5a5a   메타 (6.05:1)
--faint   #9c9b96   비활성 (2.71:1, 의도한 값)
--rule    rgba(17,17,15,.10)
--ease    cubic-bezier(0.22, 1, 0.36, 1)
--fast    180ms
```

색 강조는 없다. **검정이 곧 강조**이며 화면당 두 곳까지만 면으로 쓴다 — 선택된 목차 줄, 그리고 코스(마커 · 번호 · 경로선). §4.2의 흑백 마커 체계가 그대로 유효하다.

`#e61919`은 곧 끝나는 행사 표시에만 남긴다.

### 5.3 서체

```css
--font-display: "Sora", "Pretendard Variable", Pretendard, "Apple SD Gothic Neo", sans-serif;
--font-body:    "Inter", "Pretendard Variable", Pretendard, "Apple SD Gothic Neo", sans-serif;
```

**Sora와 Inter에는 한글 글리프가 없다.** 브라우저가 글리프 단위로 대체하므로 라틴과 숫자는 Sora·Inter가, 한글은 Pretendard가 받는다. 이 순서가 곧 규칙이다.

따라서 이 시스템의 인상은 **숫자와 라틴 레이블이 진다**. 목차의 개수, 코스 번호, 소요시간, `SEOUL` 같은 영문 메타가 Sora 700 · `font-variant-numeric: tabular-nums` · 자간 `-0.02em`으로 간다.

### 5.4 메타 레이블

한글에는 대문자가 없어 `text-transform: uppercase`가 아무 일도 하지 않고, 자간 `0.18em`은 한글에서 지나치게 벌어진다.

- 라틴 메타 — 11px · `0.18em` · uppercase · weight 500
- 한글 메타 — 11px · `0.14em` · uppercase 없음 · weight 500

### 5.5 형태와 모션

- 그림자 없음. 기존 `box-shadow` 10곳을 제거한다
- radius는 0이 기본. CTA와 마커만 `9999px` 알약. 현재 흩어져 있는 7 · 12 · 14 · 18px을 정리한다
- 면 구분은 1px 헤어라인. 카드를 상자로 두르지 않는다
- 전환은 `180ms cubic-bezier(0.22, 1, 0.36, 1)`. 기존 `--ease-out-soft`를 대체한다
- 지도 타일은 `grayscale(1) contrast(.82) brightness(1.1)`에 `mix-blend-mode: multiply`를 유지한다. 종이 온기가 지도까지 이어진다

## 6. 경로 계산

Mapbox Directions API로 도보 경로를 얻는다. 서울에서 walking · driving · cycling 모두 동작하며 한글 도로명이 온다. 대중교통은 Mapbox가 지원하지 않으므로 이번 범위는 **도보 전용**이다. 동네 단위 코스라는 전제와 맞는다.

- **한 번에 전 구간.** 정류를 순서대로 waypoint에 넣으면 `legs[]`에 구간별 `duration`과 `distance`가 함께 온다. 구간마다 호출하지 않는다.
- **호출 시점.** 담기 · 빼기 · 순서 변경 시 300ms 디바운스. 코스 변경은 드물어 캐시 계층을 두지 않는다.
- **실패 시.** 직선거리(Haversine)와 도보 속도 4km/h로 대략값을 내고 "약"을 붙여 표시한다. 지도가 깨지는 대신 덜 정확한 값을 보여준다.
- **한도.** 무료 100,000회/월. 여유가 크다.

순서 최적화는 Optimization API(`optimized-trips/v1`)를 쓴다. 버튼을 눌렀을 때만 호출하며, 응답의 `waypoint_index`대로 트랙을 재배열한다.

## 7. 상태와 공유

### 7.1 useItinerary

이미 있는 훅이 순서 있는 `string[]`을 localStorage에 넣고 `useSyncExternalStore`로 구독한다. 저장 형태를 바꾸지 않으므로 기존 사용자 데이터가 살아 있다. 두 함수를 더한다.

```ts
reorder(from: number, to: number): void
clear(): void
```

### 7.2 링크 공유

```
/course?s=id1,id2,id3
```

id를 순서대로 잇는다. 무드는 넣지 않는다 — 장소가 이미 정해져 있으므로 불필요하다. 직렬화는 `join(",")`, 복원은 `split(",")` 후 조회다. 존재하지 않는 id는 조용히 건너뛴다. 데이터가 바뀌어 항목이 사라져도 링크가 깨지지 않는다.

## 8. 확인 방법

순수 로직만 검증한다. 렌더링 테스트는 이번 범위가 아니다.

| 대상 | 확인할 것 |
| --- | --- |
| URL 직렬화 | id 배열 → 문자열 → id 배열 왕복이 같은가. 없는 id가 걸러지는가 |
| `reorder` | 앞→뒤, 뒤→앞, 경계값에서 순서가 맞는가 |
| Haversine fallback | 알려진 두 지점의 거리와 시간이 합리적 범위인가 |
| 체류 시간 합산 | `place`와 `event`가 섞인 코스의 총 시간이 맞는가 |

이 저장소에는 테스트 러너가 없다. Vite 프로젝트이므로 `vitest`를 devDependency로 하나 더한다. 설정 파일 없이 동작한다.

## 9. 아직 막힌 것

1. **`enriched.json`이 저장소에 없다.** 수집한 19곳(신촌 7 · 약수 6 · 빵집 6)은 다른 세션의 산출물이라 읽을 수 없다. 병합의 선행 조건이다.
2. **19곳의 설명문을 새로 써야 한다.** 원 출처의 문구는 쓸 수 없다.
3. **출처 판단이 남아 있다.** 19곳은 큐레이션 미디어 게시물에서 왔다. 문구를 새로 쓰고 `sourceLabel`을 붙여도 장소 선택 자체가 그쪽의 편집 결과다. 발굴 단서로 쓰는 것과 그대로 싣는 것 사이의 판단이 필요하다. 이 결정은 데이터에만 영향을 주고 위 설계는 바뀌지 않는다.

## 10. 데이터 현실

전체 43개 중 상설 장소는 4개다. 수집한 19곳을 더해도 무드 두 개(음반 · 헌책, 산책)는 비어 있다. 도보 코스는 1~2km 안에 3~5곳이 필요한데, 지금 그 밀도를 만족하는 곳은 신촌과 약수 · 버티고개뿐이다.

설계는 이 사실 위에서 동작해야 한다. 빈 무드를 `—`로 적고, 무드 밖 장소를 흐리게 남기고, 실제 밀도가 있는 동네부터 검증하는 선택은 모두 여기서 나왔다.
